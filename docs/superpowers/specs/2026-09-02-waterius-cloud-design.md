# Дизайн: HACS-интеграция Waterius Cloud

Дата: 2026-09-02
Статус: утверждён пользователем, готов к планированию реализации

## Задача

Забирать показания счётчиков из личного кабинета `https://account.waterius.ru/` и публиковать их
сущностями в Home Assistant.

Прибор Waterius стоит на объекте, недоступном из сети Home Assistant, поэтому штатные пути
(MQTT или HTTP POST напрямую с устройства) неприменимы. Облако — единственный канал.

Интеграция **только на чтение**. Единственное действие наружу — запрос принудительного обновления
источника, и то лишь когда облако само его разрешает.

## Что выяснено про API (разведка 2026-09-02)

Кабинет — Vue-SPA поверх Django REST Framework с dj-rest-auth. HTML парсить не нужно.

### Авторизация

- `POST /dj-rest-auth/login/` с `{email, password, brand: "waterius"}` возвращает `{key: ...}`.
- **Логин защищён Google reCAPTCHA**: без поля `recaptcha_response` сервер отвечает
  `{"email": ["Проверка Google reCAPTCHA не пройдена..."]}`. Логиниться из кода нельзя,
  и обходить капчу мы не будем.
- `Authorization: Token <key>` API принимает: на подставной токен `/api/user/` отвечает
  `{"detail": "Недействительный токен."}`, то есть `TokenAuthentication` включён.
  Без заголовка — `{"detail": "Учетные данные не были предоставлены."}`. `Bearer` не поддерживается.
- Токен DRF постоянный, срока жизни не имеет. Оговорка: dj-rest-auth **по умолчанию** удаляет токен
  на `POST /dj-rest-auth/logout/`, то есть кнопка «Выход» в веб-кабинете, скорее всего,
  инвалидирует токен интеграции. На реальном аккаунте это не проверялось (проверка означала бы
  разлогинить пользователя). README должен рекомендовать закрывать вкладку, а не выходить;
  на случай, если токен всё же отвалится, есть reauth.

**Вывод:** токен добывается вручную один раз (DevTools, ответ `/dj-rest-auth/login/`) и вводится
в config flow. Пароль в Home Assistant не попадает.

### Данные

Одного запроса достаточно для всего:

```
GET /api/source/?page=1     ->  {count, next, previous, results: [source, ...]}
```

Каждый `source` содержит вложенный список `channels`. Отдельные запросы к `/api/channel/...`
не нужны. `GET /api/channel/realtime_values` на реальном аккаунте вернул `[]` — не используем.

Используемые поля `source`:

| Поле | Назначение |
|---|---|
| `id` | идентификатор устройства HA |
| `name`, `place` | имя устройства |
| `last_wakeup` | ISO 8601 UTC, последний выход на связь |
| `period_min` | период пробуждения прибора, мин (в тестовом аккаунте 1440) |
| `outdated` | облачный флаг «данные устарели» |
| `can_refresh` | разрешено ли принудительное обновление |
| `battery` | заряд, % |
| `voltage`, `voltage_low`, `voltage_diff` | напряжение батареи, В |
| `version_esp`, `version` | версия прошивки, вместе дают `sw_version` вида `1.1.20-32` |
| `mac` | `connections` устройства HA |
| `warnings` | список предупреждений облака |
| `channels` | вложенные каналы |

Используемые поля `channel`:

| Поле | Назначение |
|---|---|
| `id` | идентификатор сущности |
| `data_type` | тип ресурса, см. справочник ниже |
| `last_value` | показание счётчика |
| `number` | номер входа прибора (0/1) |
| `is_work`, `warnings` | признак проблемы |
| `monthly_diff`, `monthly_limit`, `consumption_since_reset` | атрибуты |
| `factor`, `serial`, `counter_id`, `service_date`, `info` | атрибуты |
| `manual_last_value` | признак ручной правки показания (см. риск ниже) |

### Чего в облаке нет

- **Архива показаний.** `GET /api/channel/{id}/value/` возвращает 405 (эндпоинт только на запись,
  для ручного ввода). `GET /api/channel/{id}/reports` — пусто (это отчёты об экспорте в УК).
  `GET /api/channel/{id}/statistic/{год}` даёт только помесячные дельты.
  **Бэкфилла истории не будет, статистика в HA стартует с нуля.**
- **RSSI** и других радиопараметров, кроме `wifi_channel` и `wifi_connect_errors`.

### Тупиковые направления (проверены, не подходят)

- Раздел «Умный дом» в кабинете (`SmartHomePlatform`) описывает **отправку** показаний
  из Home Assistant в облако через `rest_command` на `uc.waterius.ru`. Направление обратное.
- `/api/export/*` и `/api/report/*` — передача показаний в управляющие компании, не источник данных.

### Справочник `data_type` (`GET /api/catalog/datatypes/`)

0 Холодная вода · 1 Горячая вода · 2 Электричество · 3 Газ · 4 Отопление (ГКал) ·
5 Электричество (День) · 6 Электричество (Ночь) · 7 Электричество (Пик) ·
8 Электричество (Полупик) · 9 Питьевая вода · 10 Другой · 11 Электричество (всего) ·
12 Отопление (КВт) · 13 Водоотведение · 14 Отопление (ГДж) · 15 Горячая вода (недогретая)

Справочник статический, зашивается в `model.py` константой, а не запрашивается при каждом опросе.

## Архитектура

Один config entry = один аккаунт Waterius. Один `DataUpdateCoordinator` на entry тянет
`GET /api/source/` и раскладывает результат по индексу. Каждый `source` — устройство HA,
каждый `channel` — сущности. Один HTTP-запрос на цикл опроса независимо от числа приборов.

Отвергнутые варианты: entry на каждый прибор (пользователь добавляет каждый руками, N запросов
вместо одного, гибкость по интервалам никому не нужна при пробуждении раз в сутки);
сущности без координатора (N×M запросов, рассинхрон значений, негде централизованно обработать 401).

### Модули

Репозиторий `coolexer/ha-waterius-cloud`, лицензия MIT, структура по образцу `ha-razliv-snt`.
Домен `waterius_cloud` — намеренно не `waterius`, чтобы не столкнуться с возможной официальной
интеграцией.

| Модуль | Ответственность | Зависимости |
|---|---|---|
| `api.py` | HTTP-клиент: заголовок `Authorization: Token`, пагинация `/api/source/`, `GET /api/user/`, `POST /api/source/{id}/update`. Свои исключения. Не знает про Home Assistant | `aiohttp` |
| `model.py` | Разбор JSON в датаклассы `WateriusDevice` / `WateriusChannel`, таблица `data_type` → (`device_class`, единица), вычисление признака офлайна. Чистые функции | — |
| `coordinator.py` | `DataUpdateCoordinator`, индексы по `source_id` и `channel_id`, трансляция исключений | `api`, `model` |
| `config_flow.py` | Ввод и проверка токена, `unique_id`, reauth, options flow | `api` |
| `sensor.py`, `binary_sensor.py`, `button.py` | Описания сущностей поверх координатора | `coordinator` |

`model.py` отделён от `api.py` намеренно: маппинг `data_type` — место, где вероятны правки
(16 типов, из них на реальном аккаунте проверены два), и он должен покрываться тестами без HTTP.

## Сущности

### На канал

**`sensor` — показание.** `unique_id = "channel_{id}"`, `state_class = total_increasing`,
`device_class` и единица по `data_type`. Атрибуты: `monthly_diff`, `monthly_limit`,
`consumption_since_reset`, `factor`, `serial`, `counter_id`, `number`, `service_date`, `info`.

**`binary_sensor` класса `problem`.** Включён при `is_work == false` или непустом `warnings`;
сам список — в атрибуте.

Маппинг `data_type`:

| `data_type` | `device_class` | Единица |
|---|---|---|
| 0, 1, 9, 13, 15 | `water` | м³ |
| 3 | `gas` | м³ |
| 2, 5, 6, 7, 8, 11, 12 | `energy` | кВт·ч |
| 4 | `energy` | Гкал |
| 14 | `energy` | ГДж |
| 10 «Другой» | нет | нет |

Для типа 10 `device_class` и единица не выставляются: содержимое неизвестно, а неверная единица
испортит долгосрочную статистику.

**Принятый риск.** Поле `manual_last_value` показывает, что показание правится в кабинете вручную,
в том числе вниз. `total_increasing` воспримет это как сброс счётчика и запишет фиктивное
потребление. Вариант выбран сознательно как штатный для счётчиков; лечение разовое —
чистка часа через «Разработчик → Статистика». В README это должно быть описано.

### На прибор

Устройство HA: `identifiers = {(DOMAIN, source_id)}`, `sw_version = f"{version_esp}-{version}"`,
`connections = {(CONNECTION_NETWORK_MAC, mac)}`, `manufacturer = "Waterius"`.

- `sensor` заряд батареи, % — `device_class: battery`, `entity_category: diagnostic`
- `sensor` напряжение, В — `device_class: voltage`, `entity_category: diagnostic`
- `sensor` последний выход на связь — `device_class: timestamp`, `entity_category: diagnostic`
- `binary_sensor` `connectivity` — онлайн при `outdated == false`; дополнительно прибор считается
  офлайн при `now - last_wakeup > 2.5 × period_min` (страховка на случай, если облако не выставит
  флаг; при `period_min = 1440` порог ≈ 2.5 суток)
- `button` «Обновить сейчас» — `POST /api/source/{id}/update`, `available` только при
  `can_refresh == true`. На реальном приборе Waterius сейчас `false`, кнопка будет недоступна —
  это честное отражение того, что спящий прибор разбудить нельзя.

### Опрос

Интервал по умолчанию 1 час, меняется в options flow, нижняя граница 15 минут.
Прибор просыпается раз в сутки, чаще опрашивать облако бессмысленно.

## Поток данных и ошибки

Координатор → `api.get_sources()` (идёт по `?page=N`, пока `next != null`) →
`model.parse_sources()` → `WateriusData{devices: {source_id: WateriusDevice(channels={...})}}`.
Сущности читают из индекса по своему id.

Пропавший из ответа id → сущность становится `unavailable`. Автоудаления нет: удаление сущностей
должно оставаться решением пользователя.

Появление нового прибора или канала подхватывается без перезагрузки: слушатель координатора
вызывает `async_add_entities` для незнакомых id.

Исключения `api.py` и их трансляция:

| Исключение | Причина | Действие координатора |
|---|---|---|
| `WateriusAuthError` | 401, 403 | `ConfigEntryAuthFailed` → HA открывает reauth |
| `WateriusRateLimitError` | 429, несёт `retry_after` | `UpdateFailed`; в кнопке — `HomeAssistantError` с текстом про кулдаун |
| `WateriusConnectionError` | таймаут 30 с, 5xx, сетевые сбои | `UpdateFailed` |

## Config flow

Шаг `user`: единственное поле — токен. Проверка через `GET /api/user/`.
`unique_id` = поле `user` из ответа, заголовок записи = `email`. Повторное добавление того же
аккаунта отсекается `_abort_if_unique_id_configured`.

Шаг `reauth`: новый токен с проверкой, что `user` совпадает с сохранённым; иначе `abort`
с причиной «это другой аккаунт».

Options flow: интервал опроса.

Инструкция по добыче токена — в описании шага (`strings.json`, `translations/ru.json`) и подробно
в README, вместе с предупреждением про «Выход» в веб-кабинете.

## Тесты

`pytest` + `pytest-homeassistant-custom-component`.

Фикстуры: `tests/fixtures/sources.json` — реальный ответ аккаунта, обезличенный (`mac`, `local_ip`,
`esp_id`, `key`, `email` заменены), дополненный синтетическими каналами всех 16 типов.

- `test_model.py` — все 16 `data_type` → единица и `device_class`; порог офлайна;
  устойчивость к `None` и отсутствующим полям
- `test_api.py` (`aioresponses`) — пагинация, 401, 429, 500
- `test_config_flow.py` — успех, `invalid_auth`, `cannot_connect`, дубль аккаунта,
  reauth на чужой аккаунт

## Вне объёма

- Запись показаний в облако и передача показаний в управляющие компании.
- Восстановление истории: облако её не отдаёт (см. «Чего в облаке нет»).
- Поддержка источников не-Waterius (Saures и прочие, заводимые через `/api/source/saures/*`):
  структура каналов у них та же, так что они, скорее всего, заработают сами, но целью не являются
  и тестами не покрываются.
- Авторизация по паролю, телефону, magic link, Яндекс и VK — все проходят через капчу.
